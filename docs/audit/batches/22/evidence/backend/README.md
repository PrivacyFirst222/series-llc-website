# Batch 22 backend evidence

Scope: B3-03 email-change send truth, B3-05 100-owner operating-agreement capacity, B6-01 explicit company selection.

The final `server/batch22-check.ts` harness runs the real Hono routes against a fresh, disposable PGlite database and local file storage. The environment is proved offline before testing. Its only fake transport is a fetch implementation that accepts exactly the Resend email endpoint and refuses every other destination; no real email or remote service is used. PDF generation, authentication, database queries, ownership checks, and downloads are real.

`red-final.log` runs the identical final harness against baseline 53327cf from a temporary `git archive`, with the installed dependencies linked and no product files altered. `green-final.log` runs the repaired implementation. The baseline has 27 failing and 6 passing rows; the repaired run passes 33 of 33 rows. The new in-flight concurrency controls fail on the baseline because it responds immediately (200), but the baseline already leaves the newer token active. The actual older-request supersession defect was introduced by the first awaited-send implementation and is reproduced separately in concurrency-before.log, not attributed to the baseline. Eleven rows each exercise six invalid company values (nonexistent, another account, unpaid, empty, malformed and whitespace), compare business tables before/after, and require the specific company-selection error. Two more rows exercise explicit null/number/object selections in body-based routes. Omitted company and valid selection remain positive controls.

The 100-owner case saves and reloads the complete answers object with structural equality, verifies 101-entry refusals leave the saved draft unchanged, and generates each of the four multi-member master variants. Each actual downloaded PDF is read with pdftotext and all 100 names are required. The stored generation must retain all 100 contributions ($100 each). Fifty paired ownership units are also saved and generated, with both signatories and each $200 contribution verified. The four PDFs and extracted text are retained in green/ for visual review. No master or legal wording changed.

Mail checks cover rejected transport, absent provider acceptance ID, delayed acceptance, separate old-address warning failure, successful retry, unchanged sign-in until confirmation, password reset during the send, and a slow older request overtaken by a later successful request (different and same address), plus overlapping same-address activations. The latter race was found during parent review of the first implementation; `concurrency-before.log` records it before adding the optimistic activation check. The check binds activation to the original account email, pending email, verification token identities, password hash, live session and PostgreSQL row version (xmin). A failed new send leaves the earlier pending request and token untouched.

Intermediate red.log included a harness expected-row-count error (28 actual versus 30 expected), and the first green.log compared JSON string order rather than structure. Neither setup/comparison error is claimed as product regression evidence; red-final.log and green-final.log supersede them. Logs in red/ and green/ retain expected mocked transport refusal details.

Tooling deviation: a mistakenly invoked `bunx tsc` at repository root fetched compiler dependencies into Bun's cache. It was not an authorized installation and was stopped/reported to the parent. No root package.json, node_modules, bun.lock or bun.lockb appeared, and git diff showed no lockfile change. No cache or pre-existing lockfile was removed. Subsequent typechecks use the installed `webapp/node_modules/.bin/tsc` directly. The downloaded compiler's baseUrl diagnostic was not acted on.
